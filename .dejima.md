# Working on dejima-devbox-hardener

Notes for an agent working **on this repo**. Not a description of what the tool
does: `README.md` and `docs/threat-model.md` are that.

## An upgrade note is a procedure, not a description

Somebody follows it verbatim, on a machine they are partway through changing,
often at a scheduled window with sessions drained. A step that does not work
stops them where they stand, and the failure looks like the upgrade rather than
like the note.

Three ways notes here have gone wrong, all shipped, all caught by an operator
running them:

- **naming a command the tool does not have.** v6 said
  `dejima-devbox-upgrade mark-guest 6`. There is no `mark-guest`: bootstrap
  records the guest version itself, because that is the half a box can know
  about itself, and `mark-node` is for the half it cannot see.
- **naming a command the operator's copy has not got.** The installed copy
  carries the notes it was installed with, so a note that tells a box at v4 to
  run the installed tool for v5 gets "no upgrade note for v5" - true of that
  copy, false of this repository. Use `./bin/` when the upgrade does not run
  bootstrap first.
- **naming a command in a form their deployment does not have.** See below.

Tests in `test/upgrade.bats` and `test/guard-shell.bats` hold all three. They
are cheap to extend and worth extending whenever a note starts telling an
operator to run something new.

## A note that runs dejima-guard needs the container form too

dejima-guard usually runs as a Docker container, so `dejima-guard accept` on
that host is command-not-found. Worse if the operator also installed the host
path at some point: the bare name then finds a **second deployment**, with its
own baseline and its own idea of what normal looks like, and answers as though
nothing were wrong.

So any note that tells the operator to run a guard command carries a short
**Running it in Docker?** block naming the prefix:

```sh
docker compose exec dejima-guard dejima-guard accept
```

Point at [dejima-guard](https://gitbox.branderson.io/dejima/dejima-guard)'s own
README for the rest rather than copying its interface here, where it would go
stale without anything noticing. `test/guard-shell.bats` fails a note that runs
the guard without the block.

## Two version numbers, and only one of them is yours to assert

`guest_version` is written by `dejima-devbox-bootstrap` when it installs, since
a box can see what is installed on it. `node_version` is recorded by
`dejima-devbox-upgrade mark-node`, because the console work happens where no
guest can look, so the operator asserting it is the only evidence there is.

A note with node work says so and ends in `mark-node`. A guest-only note ends in
bootstrap and marks nothing.

## Changing what `drift` collects changes every deployed baseline

The state's line format is an interface: dejima-guard diffs today's against one
it recorded weeks ago. Adding a field to a `PORT` line, or a new line kind, makes
every existing baseline differ on every line of that kind, which arrives as an
alert on somebody's phone.

That earns a version bump and a note saying to re-accept, on the guard if there
is one. It is not a reason to avoid the change: v6 widened collection precisely
because the old paths all needed root to write, and a dejima session does not
have root.
